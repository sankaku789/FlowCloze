FlowCloze 最終改修計画

Adaptive Compose Plannerを実行計画の骨格とし、Markdown解析・固定フィールド・検証をCoreに残したまま、batch対応のQuestionComposerドメインポートとprovider adaptersを段階導入する。

対象: 現行 src/ と2件の設計資料更新: 2026-07-31文書: 実装着手用の最終計画

1. 結論と設計原則

Coreの主導権

変更可能な業務データはquestion本文（空欄を含む）のみ。Core採番のidは相関用opaque echoとして応答に含めるが、新規生成・変更は禁止し、section、type、targets、answers、source_text、順序はParser/Assemblerが決定する。

ポートの単位

汎用LLMではなく教材用途の文章合成を表す QuestionComposer を公開する。batchは実行最適化、qblock/taskは意味単位として分離する。

失敗の扱い

通信再試行・内容再試行・最終fallbackを分離する。既定は品質を隠さない明示的エラー。決定的draftへのfallbackはCLIで選択可能にする。

3. QuestionComposerポート（batch対応）

単件traitを先に作って後でbatchを足すと、plannerが再びprovider固有呼び出しへ戻るため、最初からbatchを契約に含める。

pub trait QuestionComposer: Send + Sync {
    fn compose_batch(&self, request: &ComposeBatchRequest)
        -> Result<ComposeBatchOutput, ComposeError>;
}

struct ComposeBatchRequest {
    schema_version: u32,
    batch_id: String,
    tasks: Vec<ComposeTask>,       // idはCoreが採番。LLMに生成させない
    style: WritingStyle,
    prompt_version: String,
}
struct ComposeTask {
    id: String, source_text: String, scaffold_question: String,
    answers: Vec<String>, blank_token: String, blank_count: usize,
}
struct ComposeBatchOutput { items: Vec<ComposedItem>, metadata: ComposeMetadata }
struct ComposedItem { id: String, question: String }
enum ComposeError { Configuration, Authentication, RateLimited(Option<Duration>),
 Timeout, Transport, Api { status: u16, message: String, retryable: bool },
 InvalidResponse, EmptyResponse }

ComposeErrorのretry契約:

通信retryとcontent retryの分類
分類variant処理・上限
HTTP/transport retryRateLimited、Timeout、Transport、Api { status, retryable: true }指数backoff＋Retry-After。初回を含む最大3試行。
content retryInvalidResponse、EmptyResponse、parse/欠落・空欄不一致制約feedback付きtask単位で最大2回。通信retryと別カウンタ。
即時終了Configuration、Authentication、Api { retryable: false }再試行せずfallbackまたはstrict error。
  • PlannerはComposeBatchRequestを作り、成功taskをCollectorへ渡す。失敗taskだけをsingle-task queueへ戻す。
  • IdentityComposerはdraftを返すテスト実装。GeminiAdapter/OpenAiCompatibleAdapterは通信と変換のみ担当。
  • providerがbatch非対応でもadapter内で逐次化し、外部契約は変えない。

4. Adaptive Compose Planner契約

Planner状態遷移と再試行上限
状態遷移条件・上限
Batched成功→done / parse・欠落→SingleTaskbackend別 max_tasks_per_batch と推定token上限。
SingleTask成功→done / 再失敗→errorまたはfallbackmax_retry_countを超えない。document全体は再生成しない。
将来のSegmented単独でも巨大なtaskのみ初期計画では未導入。context_before/target/afterと全体再検証が必須。

初期値: Geminiは8 task/12,000 token/最大3並列、Localは2 task/4,000 token/逐次。MVPでは逐次実行とし、max_concurrent_batchesは未使用扱い（後続フェーズで有効化）にする。文字数推定はprompt固定部分と追加制約も加味し、安全側のヒューリスティックとして使う（課金計算には使わない）。

attempt/idempotency: 各taskはrun_id + task_id + attemptをキーにする。duplicate/unknown/missing IDは成功扱いにせず再計画し、成功確定taskを後続retryで上書きしない。

失敗理由別の再計画

  • JSON parse error: batchを縮小。
  • missing id/task: 該当taskを単独化。
  • blank count mismatch・leakage: 制約フィードバック付き単独retry。
  • 認証・設定・恒久的4xx: retryせず共通エラー。

6. Validation強化：target spanとplaceholder

現行はanswer文字列のreplace置換と＿＿＿個数に依存し、target spanは未保持である。そのため同一answerの複数出現、Unicode類似文字、LLMによる空欄幅変更で誤判定し得る。

座標系: target spanはParserがMarkdownのtarget構文を認識した時点で記録する、正規化前のraw qblock body上のUTF-8 byte offset（start inclusive/end exclusive）とする。answer文字列の再検索や最長一致ではspanを決めない。NFC/NFKC、trim、改行変換はspan決定後に行い、座標計算へ使わない。異なるspanに同じanswerがある場合は入力順の別targetとして許可し、同一spanの二重登録は構文エラーにする。内部ではtargetごとに一意なsentinelを割り当て、LLM応答でsentinelの集合と順序を検証した後、最終表記＿＿＿へ正規化する。

  1. Parserでtargetのbyte span／文字境界と出現順を保持する（既存schemaは維持し、内部型に追加）。
  2. placeholderを単一定数として正規化し、全角下線・半角下線・連続空白の受入範囲を明示する。最終出力は＿＿＿へ正規化。
  3. MVPのtask単位errorは、空文字、sentinel集合・順序不一致、明白なanswer完全一致漏洩に限定する。短縮/長文化、文体、新情報追加は機械的に完全保証できないため、設定可能な閾値によるheuristic warningとlive評価指標に分ける。
  4. document最終段でid順・件数・固定field不変を再検証する。MissingQuestion、QuestionOrderMismatch、FixedFieldMismatchを明示的な最終エラーにする。
  5. LLM出力のunknown/duplicate/missing/mutated ID、filter_mapによる欠落taskは黙って捨てずエラー化する。旧JSONは既存deserializerで読み、欠損fieldは既存既定値を適用して互換を保つ。
  6. 短い一般語のAnswerLeakage誤検知は既知の限界としてwarning/設定で扱い、仕様変更時にfixtureを更新する。

7. 設定・CLI互換性とfallback

CLI > 環境変数 > config.toml > 組み込み既定値

flowcloze generate note.md --rewrite never
flowcloze generate note.md --rewrite always --provider gemini
flowcloze generate note.md --rewrite always --provider local --batch small
flowcloze inspect-scaffold note.md
  • 現行コードは--modelを即時error扱い、api setでAPI keyを.envへ保存する実装である。最終方針では--providerを正規名とし、旧--backendをaliasとして移行期間のみ受理する。
  • --modelは互換期間のみ受理して設定を上書きし、将来は明示的なprovider設定へ移行する。新規コマンドは秘密値を保存せずapi_key_envだけをconfigに置く。既存.envは読み続け、api setは非推奨化する。
  • 解決順位は引数 > 環境変数 > config.toml > 組み込み既定値。--batchと--skip-constraintsは既存挙動を維持し、provider alias適用後に同じpolicyへ渡す。
  • 既定rewriteは現行品質を壊さない移行期間always、次majorでautoまたはneverを検討。明示的な--fallback draft|errorを追加。

Fallback方針: 組み込み既定はerror（strict、終了コード1）とし、draft fallbackは--fallback draftで明示する。fallbackはtask単位で成功taskを保持し、document単位の致命的整合性エラーは常に終了する。既存GeneratedDocumentのschemaは変更せず、fallback件数・理由・task idはstderr summaryへ出し、詳細は任意sidecarへ書く（metadataを既存JSONへ混在させない）。

資料間の差分を解消した決定: Refactoring proposalの「Identityでdraftへfallback」とAdaptive Compose Planner設計の「scaffoldを成果物にしない」は目的が異なる。最終計画では、自然化を試みた後の明示的なdraft fallbackは許可するが、inspect-scaffoldのscaffold単独出力を通常生成とは区別し、strictモードでは常にエラーとする。

9. テスト戦略

Core・golden

Parser、span、scaffold、Assembler、既存JSON/TUI/CSV/PDFを完全一致。Identity経路はAPIなしでE2E。

Port契約

Identity、Gemini、OpenAI互換に共通テスト。正常抽出、空応答、401、429、503、timeout、metadataを固定。

Planner/validation

batch成功、失敗taskだけretry、欠落id、blank mismatch、leakage、strict/fallback、token budget境界をモックで検証。

Live smoke（任意）

通常CIから分離し、実モデルの成功率・空欄一致率・漏洩率・fallback率・レイテンシを記録。

現行基準線ではcargo testの34件が成功している。ただし、これは新計画のHTTP mock、CLI互換、fallback/sidecar、target span、固定field不変条件をまだ検証しない。各Phaseで対応テストを追加し、cargo test（必須）、provider HTTP mock、必要時のみ--ignored live testを実行する。文章の完全一致はCoreに限定し、LLMは不変条件で評価する。
